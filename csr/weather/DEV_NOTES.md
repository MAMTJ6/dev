### Unique discoveries (hard-won, do not re-learn)

1. **data.gov.my forecast API sorts date-DESCENDING** — `limit=3` returns the three FURTHEST days. Fetch all, pick `date === today`. Verified live.
2. **No hourly forecast and no current-temperature exist anywhere** in MET/data.gov.my public APIs. Daily morning/afternoon/night phrases + min/max only. Don't fake it.
3. **CARTO tile hostname is `{s}.basemaps.cartocdn.com`** — an extra `.tile.` level breaks TLS (wildcard certs cover ONE subdomain level) → ERR_CERT_COMMON_NAME_INVALID, silently grey basemap. This bug was in the user's original code for the project's whole life.
4. **HTTP 429 from data.gov.my** = per-IP rate limit; dev-session reload+tab-switch bursts trip it. Fixed with 60s min-gap on visibilitychange. Page degrades gracefully (keeps last state).
5. **metapi2**: token is the blocker, NOT CORS (it sends ACAO:*). Requires start_date+end_date (400 without). RAIN dataset is NOT mirrored by data.gov.my (verified live gap) — hence the two-source split: data.gov.my=thunderstorm, proxy=rain. Keep them disjoint; no cross-source dedup exists or is needed.
6. **Marine bulletins** ("waters of"/"perairan") mention Pahang but are NOT land warnings — scope 'marine', never on the map, note-line only.
7. **BM alias**: "Tanah Tinggi Cameron" = Cameron Highlands (spotted in a real bulletin's text_bm). Alias table has it. `console.warn` on any unmatched district name — that's the discovery mechanism for new MET spellings.
8. **Fixture-text trap**: "(TEST DATA)" placed directly after "Pahang" matches the district regex. Fixtures use ". (TEST DATA)" — the period matters.

## Session 2 — `paparan/index.html` map framing (2026-08-10)

### What happened

User wanted the non-interactive `paparan/` Leaflet map to frame Pahang tighter/better instead of the plain `fitBounds` view (which either left dead space around the state on one axis, or — when I tried a "cover" zoom that fills the box completely — cropped districts off the bottom/left, which they rejected outright: no district may be cut off, ever, over filling the frame).

The fix that stuck: instead of computing a fit programmatically, I added a `?debugMap=1` query param that temporarily re-enables drag/scroll/zoom on the map (all off by default — TV has no mouse) plus an on-screen readout (`center: [lat,lng] zoom: Z`, also console-logged) so the user could hand-drag to the exact framing they wanted, then read the numbers off and tell me. Much faster than guessing padding/scale math — **prefer this "let them find it, then hardcode it" approach over programmatic cover/contain-fit math when framing is a subjective/visual call, not a computed one.**

### Landed values

```js
}).setView([3.6066, 102.7932], 8.7); // hand-tuned via ?debugMap=1 to frame Pahang
```
No `fitBounds` call anymore in `loadGeoJSON()` — the hand-tuned `setView` is final, geojson just gets added on top of it.

### Sharp edge hit (know this cold)

**`zoomSnap` rounds `setView`'s zoom too, not just interactive zoom steps.** Production had `zoomSnap: 1` (seemed harmless — map is non-interactive there) but that silently rounded `8.7` → `9` on load, so live looked more zoomed-in than the debug page (`zoomSnap: 0.1`) where `8.7` stuck exactly. User correctly clocked the visual mismatch immediately. Fix: production must use `zoomSnap: 0` (no rounding) whenever `setView` is passed a fractional zoom — don't assume a disabled-interaction map doesn't need this option tuned.

Debug-mode scroll-wheel granularity note: `zoomDelta`/`zoomSnap` only govern rounding and the +/− button step — scroll-wheel zoom has its own magnitude formula keyed off `wheelPxPerZoomLevel` (default `60`). Bumped to `600` in debug mode to get scroll increments down near `0.1` per notch; if debug zoom ever feels too coarse/fine again, that's the knob.

### Current state

`?debugMap=1` is still live in the shipped code (gated, zero effect without the param) — decide later whether to strip it before a real commit or leave it as a permanent framing-adjustment tool. Nothing from this session committed yet either, consistent with Session 1's note that the user usually handles commits.

Same fast/concrete rhythm as Session 1: screenshot → "why" → diagnosis → their call. Ran a small standalone Node script (`require('playwright').chromium.launch()`, no project `node_modules` needed) against a local `python -m http.server`, and that's what actually cracked it — direct `getBoundingClientRect()`/`getComputedStyle()`/screenshot inspection, not another round of guessing. **One Windows-specific environment note worth keeping**: `lsof` is not available in this Git-Bash environment (silently no-ops) — to find and kill an orphaned background `python -m http.server` process, use `netstat -ano | grep ':<port>' | awk '{print $NF}'` piped into `taskkill //F //PID`, not `lsof -ti:<port>`.

**The real bug, once actually found**: `transform: scale()` only shrinks what's already PAINTED — it does not retroactively un-clip content that `overflow: hidden` already discarded based on the box's PRE-transform size. My scale value was mathematically "correct" by my own formula, but `overflow: hidden` was clipping the content down to whatever fit in the ORIGINAL unscaled box BEFORE the scale ever got a chance to act on it — so the visible result was always just a cosmetically-shrunk version of the same truncated subset (legend + forecast + thunder + rain-card-HEADER only, never the actual tier rows), no matter how the scale number was tuned. **This is the single most important thing to remember from this session, general enough to bite anywhere: `overflow: hidden` + `transform: scale()` on the same element is not "clip to X, then shrink the overflow into view" — clipping happens against the untransformed box, full stop, and scale can only shrink what survived that clip.** The fix is to keep `overflow: visible` and let the scale (computed as `available / needed`) shrink the WHOLE unclipped content, which — by construction — lands its rendered height at exactly `available`, with nothing left to clip at all.

Fixing this for desktop worked cleanly and verified with an exact-match screenshot (all three tiers fully visible, correctly scaled). Fixing it for MOBILE surfaced two more real, non-obvious bugs on top:
1. **A CSS spec gotcha, confirmed via `getComputedStyle`, not guessed**: when `overflow-x` and `overflow-y` disagree on visible-ness (one `visible`, one not), the browser silently computes the `visible` one AS `auto` instead of honoring it. Mobile's base rule sets the `overflow: hidden` SHORTHAND (both axes) for the collapsed peek state; my override only touched `overflow-y: visible`, leaving `overflow-x` stuck at `hidden` from the base rule — which silently downgraded my `overflow-y: visible` back into `overflow-y: auto`, quietly reintroducing the exact clip-before-scale bug I'd just fixed, on mobile only. Fix: override the `overflow` SHORTHAND, not just the one axis, whenever you need BOTH to actually be visible.
2. `transform-origin` had to be the box's own TOP regardless of whether the box is CSS-anchored via `top` (desktop) or `bottom` (mobile's sheet) — content always flows downward starting from the box's top edge no matter which CSS property pins its position, and anchoring the scale-shrink there is what makes the shrunk content land flush against BOTH edges of the available budget. Anchoring at "bottom" instead (my first instinct for a bottom-anchored sheet) left the result floating mid-sheet, not reaching either edge cleanly.

Then, once content was genuinely all visible on mobile, the user caught a real cosmetic regression from the fix itself: **"i see the bottom sheet is floating at the center"** — uniform `scale()` shrinks width right along with height, and a horizontally-centered origin pulls a full-width sheet away from both screen edges into a smaller floating card. Asked directly via AskUserQuestion whether to accept that trade-off or force full-width back; user picked full-width. The fix: deliberately WIDEN the box before scaling, by exactly `1/scale`, so the two cancel out and the rendered width lands back at 100% while only the height still nets-compresses — complicated by the fact that widening a box changes how its OWN content wraps (fewer forced line-breaks), which changes `scrollHeight`, which changes the ideal scale, which changes how much to widen by. Solved with a small (2–3 pass) iterative convergence loop rather than a closed-form formula — real content converges fast since wrapping is basically monotonic with width. **Hit a second, sneaky CSS conflict on the very first attempt at this**: mobile's `max-width: 100%` rule was silently clamping the deliberate over-width right back down to 100%, defeating the whole compensation before it could do anything — needed an explicit `max-width: none` override alongside the width override while it's active.

Final state, verified via the same Playwright harness with screenshots at every step: full-width edge-to-edge mobile sheet (matching a native bottom-sheet look), all three tiers fully visible on both desktop and mobile, zero scroll anywhere, and the user still needs to confirm it on their own real device/browser since everything here was checked in headless Chromium, not their actual phone.
